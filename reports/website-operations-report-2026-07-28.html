網站現況與任務處理模型

這份報告回答兩件事：正式網站目前如何從內容檔產生頁面，以及從 30 份 HTML 留下的軌跡來看， 系統如何理解、試作、修正並交付你指派的任務。

01 / Core reading

它是一個內容驅動的靜態 Wiki，加上一套以 Demo 為核心的任務協作流程。

正式網站與資料夾裡的 HTML 有明確分工：Next.js 程式碼負責真正的網站； 30 份 HTML 多半是設計提案、問題重現、比較稿與工作報告，不是正式網站的 runtime 模組。

Code confirmed

正式網站

`content/episodes/*.md` 是內容來源，`src/lib/markdown.ts` 在 build 時讀取並解析， 首頁和 8 個單集頁由 Next.js App Router 預先產生。沒有資料庫、登入、後台 CMS 或 API。

Artifact inferred

任務協作

從檔名與內容可看出常見做法是先建立獨立 HTML Demo，呈現 Before／After 或多方案， 再把選定結果移植到 React 正式版。

Semi automated

內容生產

字幕下載、VTT 清洗、詞庫替換與網站建置可以用腳本處理； 說話者判斷、語意重組、翻譯與最終查核仍需人或 AI 工作階段介入。

Important boundary

HTML 報告的敘述不等於目前程式的事實

例如 `opus_audit_report.html` 宣稱「20/20、已達生產級」， 但本次實際檢查仍有 27 個 lint errors；`demo_correction_pipeline.html` 顯示 42 terms， 實際 `glossary.json` 已有 47 筆。報告是當時快照，不是持續同步的狀態頁。

02 / Runtime

網站從 Markdown 出發，在 build 階段完成大部分工作。

這種架構適合 Vercel：內容變更後重新 build，使用者收到的是預先產生的頁面； 瀏覽器端只負責顯示模式、偏好設定與圖卡匯出。

Source

Frontmatter、精簡總結、段落紀錄、完整逐字稿集中在 `content/episodes/ep01.md` 到 `ep08.md`。

`generateStaticParams()` 列出 8 集；首頁、404 與單集頁在 production build 產生。

Browser

互動與個人偏好

React client components 處理主題、時間軸、緊湊模式、焦點特效、內容模式與下載。

首頁

  • 依 episode number 由新到舊排序。
  • 最新一集使用綠色強調。
  • 時間軸、日期位置與摘要展開可切換。

單集頁

  • 顯示標題、日期、來賓與 YouTube 連結。
  • 可切換精簡總結、段落紀錄、逐字稿。
  • 非逐字稿模式可再切換圖卡或文字。

圖卡輸出

  • `CardMode` 僅在瀏覽器端動態載入。
  • `html-to-image` 把卡片轉為 PNG。
  • `JSZip` 與 `file-saver` 產生 ZIP 下載。

使用者狀態保存

Theme、時間軸、日期位置、緊湊模式和閱讀焦點存在瀏覽器的 `localStorage`。 這些偏好只存在該瀏覽器，不會跨裝置同步，也沒有帳號資料。

03 / Task model

你指派的任務，通常會走「理解、做 Demo、比較、實裝、再審查」的路線。

這是根據 HTML 檔案的命名、內容與修改時間推論出的協作模型。 專案裡目前沒有真正的 task queue、狀態機或審批資料庫。

理解要求

找出要求屬於首頁、單集頁、控制列、時間軸、逐字稿或部署。

隔離試作

先在 `public/*.html` 做不影響正式版的單檔 Demo。

呈現差異

用 Before／After、A／B／C 或淺色／暗色比較具體差異。

收斂方向

依回饋改名、修溢出、調間距、配色或資訊階層。

移植正式版

把選定設計套到 `src/components`、CSS 或內容 schema。

自審與建置

另產 audit HTML，並以 TypeScript、lint、build 驗證。

Variant comparison

`date_layouts_demo.html`、`tag_demo.html`、`settings_ui_demo.html` 用多方案比較來協助決策。

Bug reproduction

`demo_overflow.html`、`demo_spacing.html`、`timeline_fix_demo.html` 先解釋原因，再展示修正版。

Progressive refinement

`ep08_redesign_demo.html` 到 `ep08_final_demo.html` 顯示單集頁經過多輪方向調整。

Self review

`self_review_report.html` 與 `opus_audit_report.html` 把遺漏、修復與宣稱成果整理成可讀報告。

04 / Content pipeline

逐字稿流程有腳本骨架，但語意工作仍是人工與 AI 協作。

`demo_true_pipeline.html` 描述的是理想工作流；實際 repo 中確實有下載、清洗與替換程式， 但沒有自動呼叫 LLM 的程式碼，也沒有端到端的一鍵工作命令。

YouTube 來源

每集 Markdown frontmatter 保存 YouTube URL。

下載 VTT

`fetch_and_process.js` 可透過 `yt-dlp` 抓取第 1 至 7 集日文自動字幕。

機械清洗

Node／Python 腳本移除 VTT 標籤、時間格式與相鄰重複片段。

語意處理

斷句、說話者辨識與繁中翻譯由人或 AI 工作階段完成，repo 內沒有自動 LLM client。

詞庫校正

34 筆 global 與 13 筆 episode 2 規則做字串／正則替換。

寫回 Markdown

最終文字進入 `【完整逐字稿】`，再由網站 parser 讀取。

Automated

程式可以做

  • 下載既有 YouTube 自動字幕。
  • 移除 VTT 標記與部分重複。
  • 套用詞庫替換規則。
  • 把標準格式逐字稿渲染到網站。
Human or AI session

仍需判斷

  • 確認字幕是否真的聽寫正確。
  • 辨識主持人與來賓。
  • 繁中翻譯與語意重組。
  • 新增 episode-specific 專有名詞。
Not implemented

HTML 裡有，正式系統沒有

  • 可操作的 Glossary Manager 後台。
  • 逐集 correction dashboard。
  • 自動 LLM／subagent 呼叫。
  • 任務重試、版本與審批狀態。

06 / Gaps

目前最需要注意的是「狀態不一致」和「半自動流程被描述成全自動」。

這些不代表網站不能使用，但會讓未來任務接手、內容可信度與部署判斷變得困難。

Data loss in UI

第 4 集逐字稿實際存在，網站卻讀不到

Parser 只接受 [時間] [說話者] 文字； 第 4 集使用 [時間] 說話者：文字。結果是 63 行來源全部被忽略， 逐字稿頁會顯示「尚未提供」。

Public artifacts

30 份 Demo 都在 public

它們沒有被正式 UI 引用，但只要部署就可由網址直接存取，包括 audit 與部署指南。

Synthetic content

存在 mock transcript script

`process_transcripts.js` 明確含有「假造的原始出錯聽寫」，不應被誤當正式內容來源。

No task ledger

任務狀態靠檔名推測

`fix`、`final`、`proposal`、`demo` 沒有共同 task ID、核准欄位或「已實裝」連結。

Validation gap

Build 通過不等於 lint 通過

TypeScript 和 production build 成功，但 ESLint 仍回報 27 errors 與 11 warnings。

Stale narratives

報告數字會過期

Demo 顯示 42 terms，實際詞庫已有 47 筆；audit 的「生產級」也未反映新增程式與現況。

Destructive scripts

處理腳本直接覆寫 Markdown

`fetch_and_process.js` 與相關腳本會原地寫回 episode 檔，沒有備份、dry-run 或 schema validation gate。

一句話判斷 現在的系統很適合「由 AI 與你一起快速試作」，但還不是可以無人值守批次處理內容的 production pipeline。

08 / Validation

本次檢查結果與可信度界線。

報告同時保留「確認事實、合理推論、未能完成的驗證」，避免把 Demo 敘事當成正式現況。

TypeScript

通過。`npx tsc --noEmit` exit code 0。

Production build

通過。Next.js 16.2.10 產生 12 個靜態頁。

ESLint

未通過。27 errors、11 warnings。

已直接確認的事實
30 份 HTML 的標題、heading、按鈕與互動訊號；正式 React 原始碼；8 份 episode Markdown； 7 份 VTT；47 筆 glossary 規則；685 行逐字稿來源；TypeScript、lint 與 production build 結果。
由檔案軌跡推論的工作方式
「先 Demo、再比較、再實裝、再自審」是高可信推論，因為多組檔名與 HTML 內容都呈現同一模式； 但 repo 沒有 task metadata，所以無法從機器資料確定每一份 Demo 是否獲得過你的明確核准。
不能從現有資料證明的事項
無法證明所有 HTML 宣稱的修復都仍保留在最新程式、無法證明逐字稿每一句翻譯正確， 也無法證明 pipeline 能在無人工介入下端到端完成。
